## 0. 这次实践到底在干什么（一句话版）

这个过程里要学会三件事：

3. 怎么把"前缀搜索"做得**快**，而不是翻遍整个数据库（Aufgabe 2c/2d）

## 1. Docker：先把 Redis 跑起来

### 1.1 题目给的那条命令

```
docker run --name RedisPraktikum2026 -p 6379:6379 -it redis:latest
```

| 部分 | 意思 | 类比 |
|---|---|---|
| `redis:latest` | **镜像**：官方打包好的 Redis 安装包，`latest` 表示最新版（现在是 8.10） | 安装光盘 |
| `docker run` | 用镜像**新建并启动一个容器**；本地没有镜像就先从 Docker Hub 下载 | 用光盘装好一台小电脑并开机 |
| `--name RedisPraktikum2026` | 给容器起名字，以后用名字操作（`docker start/stop/exec RedisPraktikum2026`） | 给电脑贴标签 |
| `-p 6379:6379` | **端口映射**，格式是 主机端口:容器端口。Redis 在容器里监听 6379，映射后你电脑上的 Python 才能连 `localhost:6379` | 在墙上开一个洞，接到小电脑的网口 |
| `-it` | `-i` 保持输入打开，`-t` 分配一个终端：Redis 在**前台**运行，日志直接显示在窗口里，按 Ctrl+C 就停止 | 把小电脑的屏幕直接接到你面前 |

我们的脚本用的是 `-d`（detached，后台运行），这样同一个窗口还能继续执行 Python。

### 🖐 动手 1（PowerShell）

```powershell
docker ps                                   # 看正在运行的容器，应该能看到 RedisPraktikum2026
docker exec -it RedisPraktikum2026 redis-cli -n 1     # 进入 Redis 命令行（用 1 号库，不碰 0 号库里的数据）
```

进入以后提示符是 `127.0.0.1:6379[1]>`，`[1]` 就是库号。输入 `PING`，应该返回 `PONG`；输入 `exit` 退出。
以后也可以直接双击 `redis-cli.bat`，效果一样。

### ✅ 自测
1. 容器停了，数据还在吗？ → 容器只是停止，执行 `docker start` 后还在；但如果执行了 `docker rm`，数据就没了（没有挂载卷）。另外，Redis 默认会把数据存成快照写进容器里。
2. 为什么 Python 能连上容器里的 Redis？ → 因为有 `-p 6379:6379` 端口映射。

## 2. Redis 是什么

- **键值数据库**（key-value store）：每条数据都是 `键 → 值`，类似 Python 里一个巨大的 `dict`。
- **数据放在内存里**，所以很快（一次操作通常是微秒级）。导入 19 万家商家后，内存占用大约 190 MB。
- 每个**键**都对应一个**值的类型**。Aufgabe 1 要练的就是 4 种基本类型：

| 类型 | 像 Python 里的 | 典型用途 | 本实践里用在哪 |
|---|---|---|---|
| **String** | `str` / `int` / `bytes` | 缓存、计数器、存一整段 JSON | 2a：`business:<id>` → JSON 字符串 |
| **List** | `list`（两头都能进出） | 队列、消息、最近记录 | 没用到，练习用 |
| **Set** | `set`（不重复、无顺序） | 标签、去重、集合运算 | 2b：商家名 → business_id 的集合 |
| **Hash** | 小的 `dict` | 存一个对象的多个字段 | 没用到，练习用 |
| *Sorted Set* | 带分数、始终有序的 set | 排行榜、**按字母范围查找** | 2c：自动补全的索引（题目没要求，是我们加的） |

## 3. Aufgabe 1：四种类型动手练

完整命令都在 `cli/aufgabe1.redis` 里，按类型分段写了注释；真实输出在 `results/aufgabe1_session.txt`。
下面挑最重要的几条，你在 `redis-cli -n 1` 里**一条一条亲手敲**，边敲边对照右边的预期结果。

### 3.1 Strings

```
SET greeting "Hello"            → OK
APPEND greeting " Redis"        → (integer) 11        追加后的长度
GET greeting                    → "Hello Redis"
SET counter 10
INCR counter                    → (integer) 11        原子操作：多个客户端同时加也不会丢
INCRBYFLOAT counter 0.5         → "11.5"
SETEX temp 60 "tmp"             → 60 秒后自动删除
TTL temp                        → 剩余秒数
SETNX k1 "y"                    → 0，因为 k1 已经存在，NX = Not eXists 时才写
```

**要点**：`INCR` 这类命令是原子的，Redis 一次只执行一条命令，所以不会出现"两个人同时读到 10、都写回 11"的问题。

### 3.2 Lists

```
RPUSH mylist a b c              → 3          从右边放
LPUSH mylist z                  → 4          从左边放
LRANGE mylist 0 -1              → z a b c    -1 表示最后一个
LPOP mylist                     → z
BLPOP mylist 1                  → 列表空了就最多等 1 秒（B = blocking），超时返回 (nil)
```

### 3.3 Sets（2b 就是用它）

```
SADD s1 a b c d                 → 4
SADD s1 a                       → 0          a 已经在里面，Set 会自动去重
SADD s2 c d e
SINTER s1 s2                    → c d        交集
SUNION s1 s2                    → a b c d e  并集
SDIFF s1 s2                     → a b        差集
SCARD s1                        → 4          元素个数（Starbucks 有几家就是这样数出来的）
```

### 3.4 Hashes

```
HSET user:1 name "Ada" age 36 city "London"
HGET user:1 name                → "Ada"
HINCRBY user:1 age 1            → 37
HGETALL user:1                  → 所有字段和值
```

### 3.5 几个容易被问到的细节
- `GETSET`、`RPOPLPUSH`、`BRPOPLPUSH` 从 Redis 6.2 起已经**不推荐使用**，新写法分别是 `SET … GET`、`LMOVE`、`BLMOVE`。题目列了它们，所以照样练。
- `BITFIELD bf SET u8 0 200 GET u8 0 INCRBY u8 0 100` 返回 44：8 位无符号整数最大到 255，200 + 100 = 300 溢出后回绕（WRAP），300 − 256 = 44。
- `BITOP AND res a b`，其中 a = "abc"、b = "ABC"，结果是 "ABC"：小写字母和对应大写字母只差一个比特（0x20）。
- Set 没有顺序，`SMEMBERS` 每次输出的顺序可能不一样。

### ✅ 自测
1. 想统计"每篇文章被看了几次"，用什么类型、什么命令？ → String + `INCR`
2. 想知道"两个用户共同关注了谁"？ → 两个 Set + `SINTER`
3. `SADD` 同一个元素加两次，集合里有几个？ → 1 个

## 5. Aufgabe 2a + 2b：数据在 Redis 里怎么摆

题目要求的两种键：

```
business:1SWheh84yJXfytovILXOAQ   →  {"business_id":"1SWheh84...","name":"Arizona Biltmore Golf Club",...}   (String)
arizona biltmore golf club         →  {"1SWheh84yJXfytovILXOAQ"}                                              (Set)
```

对应 `yelp_redis.py` 里 `load()` 的核心三行：

```python
pipe.set(BUSINESS_PREFIX + bid, raw)          # 2a：原样保存整行 JSON
pipe.sadd(name, bid)                          # 2b：名字（小写）→ id 的集合
pipe.zadd(AUTOCOMPLETE_KEY, {name: 0})        # 2c 用的索引（下一节讲）
```

**为什么这样设计**

| 决定 | 原因 |
|---|---|
| 存**原始那一行**，不重新 `json.dumps` | 保证和源文件一字不差。重新序列化会把 `é` 变成 `é`，这个问题真的被测出来过（见第 8 节） |
| 名字转**小写** | 让 "Starbucks"、"STARBUCKS"、"starbucks" 合并到同一个 Set |
| 值用 **Set** | 同名连锁店（1,066 家 Starbucks）放在一个集合里，自动去重，`SCARD` 就能直接数 |
| 用 **Pipeline** | 不用 Pipeline 时，每条命令都要来回一趟网络，58 万条命令就是 58 万次往返，要好几分钟；Pipeline 每 5000 家打一个包，只要几十次往返，几秒钟就导完 |

### 🖐 动手 3（`docker exec -it RedisPraktikum2026 redis-cli`，**不加 -n**，也就是 0 号库里的真实数据）

```
DBSIZE                                        → 336947 = 192609 家店 + 144337 个名字 + 1 个索引
TYPE business:zQmHSe6IOiSNF84m9BVZ8A          → string
GET business:zQmHSe6IOiSNF84m9BVZ8A           → The Still（拉斯维加斯那家）的整行 JSON
TYPE "the still"                              → set
SMEMBERS "the still"                          → 两个 id
SCARD starbucks                               → 1066
```

### ✅ 自测
1. `DBSIZE` 为什么是 336,947，而不是 192,609？ → 还有 144,337 个"名字"键，再加 1 个索引键
2. 同一个文件导入两次，数据会翻倍吗？ → 不会：`SET` 会覆盖，`SADD`/`ZADD` 遇到已有的元素会忽略

## 6. Aufgabe 2c：自动补全怎么做才快（全题最关键）

需求：输入 "Star"，找出所有以 star 开头的名字。

### 6.1 三种做法对比

| 做法 | 怎么做 | 问题 |
|---|---|---|
| `KEYS star*` | 让 Redis 用通配符匹配所有键 | 要遍历全部 33 万个键，**期间会卡住整个服务器**，生产环境禁止使用 |
| `SCAN 0 MATCH star*` | 分批遍历 | 不会卡住服务器，但还是要遍历全部键：每次 1000 个，**实测 337 次请求、195 ms** |
| **✅ Sorted Set + `ZRANGEBYLEX`** | 把所有名字放进一个有序集合，分数都设成 0 | 分数相同时，Redis 按**字母（字节）顺序**排序，前缀查询就变成了"取一段连续范围"，复杂度 **O(log N + M)**，**实测 1 次请求、0.7 ms，快了约 260 倍** |

### 6.2 为什么"取一段范围"就等于"找前缀"

想象一本按字母排好的电话簿：所有以 star 开头的名字**一定挨在一起**，从 "star" 开始，到 "star" 后面接一个"最大的字符"为止。

（下面是索引里的真实数据）

```
stapley pest control     ← 范围之前，不以 star 开头
star 1 personnel         ← 第一个  [star
star 5 plumbing
…
starbucks
starbucks coffee
starbucks reserve
…
starlight nails & spa
…
starz nails
star火bbq                ← 最后一个：中文"火"的 UTF-8 字节（E7 81 AB）比 z 大，但仍然 < 0xFF
stash                    ← 范围之后，不以 star 开头
```

`yelp_redis.py` 里的 `prefix_range()` 就是在算这两个边界：

```python
lo = ("[" + prefix).encode("utf-8")     # "[" 表示包含边界本身
hi = lo + b"\xff"                        # 末尾接一个 0xFF 字节
```

**为什么是字节 0xFF？** Redis 比较的是 UTF-8 字节。0xFF 这个字节**在合法 UTF-8 里永远不会出现**，所以 "star" + 0xFF 比任何以 star 开头的字符串都大，连 `star€…`、中文名、emoji 也都包含在内。
如果写成字符 `'ÿ'`，它的 UTF-8 编码是 C3 BF，像 `€`（E2 82 AC）这种更大的字符就会被漏掉。单元测试 u10 专门检查了这个情况。

### 🖐 动手 4（在 redis-cli 里，0 号库）

```
ZCARD autocomplete:names                                       → 144337
ZRANGEBYLEX autocomplete:names "[the sti" "[the sti\xff"       → the still / the stirling club spa / the stirling room
ZLEXCOUNT  autocomplete:names "[star" "[star\xff"              → 181
ZRANGEBYLEX autocomplete:names "[star" "[star\xff" LIMIT 0 5   → 前 5 个
```

⚠️ `\xff` 只有在**交互式** redis-cli 里、写在双引号中才会被解析成那个字节。

然后试一下真正的程序：双击 `autocomplete.bat`，输入 `Star`，再输入编号看详情；直接按回车可以退出。

### 6.3 题目问的答案

| 问题 | 答案 |
|---|---|
| "Star" 能找到什么 | 181 个名字，其中有 starbucks 和 starlight nails & spa |
| **有几家 Starbucks** | 名字恰好是 starbucks 的有 **1,066** 家；加上 starbucks coffee（6 家）和 starbucks reserve（1 家），共 **1,073** 家。提交时要写明用的是哪种口径 |
| **"The Still" 有几条** | **2** 条 |
| **"The Sti" 补全出什么** | the still、the stirling club spa、the stirling room。注意 the still 只显示**一次**，因为补全列出的是**名字**，不是店 |

### ✅ 自测
1. 为什么所有分数都设成 0？ → 分数相同时，Redis 才会按字母顺序排列
2. 为什么查询前要先转小写？ → 索引里存的全是小写

## 7. Aufgabe 2d：查详情，以及 "The Still" 说明了什么

`details()` 只用两条命令：
1. `SMEMBERS "the still"` 拿到所有 id
2. `MGET business:id1 business:id2 …` **一次**取回所有 JSON（不用每个 id 发一次 `GET`）

结果：

| 地址 | 星级 |
|---|---|
| 3400 S Las Vegas Blvd, 89109 Las Vegas, NV | 3.5 ★（257 条评论） |
| 270 14 Avenue SE, T2G 0K3 Calgary, AB | 2.5 ★（8 条评论） |

**这说明了什么**（题目问 "Was sagen Sie zum Ergebnis"）：
- 这两家是**不同国家、毫无关系的两家酒吧**，既不是连锁店，也不是重复记录
- 补全只显示一个 "the still"，要查了详情才知道其实是两家店
- 所以**名字不是唯一标识**：对 Starbucks 来说"同名 = 分店"成立，对 The Still 则会把无关的店混在一起；反过来，"Starbucks Coffee"这种写法不同的名字又会被拆成两个键
- 改进办法：补全结果里显示城市；把名字规范化（去空格、去标点）；增加按城市检索的索引

## 8. 测试规范（这次重点要懂的部分）

运行：`run_tests.bat`，或 `python run_tests.py`。测试分 5 级，**按顺序执行**：

| 级 | 文件 | 测什么 | 需要什么 | 打个比方 |
|---|---|---|---|---|
| 1 冒烟 | `test_0_smoke.py` | 环境能不能跑：redis-py 能导入、能 PING 通、文件齐全、脚本能编译 | Redis | 开机看看灯亮不亮。**不亮就直接停**，后面的测试没有意义 |
| 2 单元 | `test_1_unit.py` | 纯逻辑：读 JSON Lines、名字转小写、前缀边界、详情格式 | 什么都不需要 | 单独检查每个零件 |
| 3 集成 | `test_2_integration.py` | 真的导入一份**特意构造的小数据**到 **15 号库**，检查 2a–2d 的结果 | Redis | 把零件装起来试一试 |
| 4 效率 | `test_3_locality.py` | 用 `INFO commandstats` **数 Redis 实际执行了哪些命令**：补全只用 1 次 `ZRANGEBYLEX`，从不用 `KEYS`/`SCAN`；详情只用 `SMEMBERS` + `MGET`；导入确实走了 Pipeline | 已导入的数据 | 不光看结果对不对，还看"走的路线对不对" |
| 5 完整性 | `test_4_integrity.py` | 19 万条数据**逐条**和源文件比对；名字集合和索引**逐个**比对；题目答案用**纯 Python 独立再算一遍**来核对 | 已导入的数据 + business.json | 全面盘点库存，再请第三方复核 |

**几条规范：**
- **测试用真实的服务**，不用假的模拟对象；测试数据放在单独的库（15 号），**绝不碰**真实数据所在的 0 号库
- **固定样本**（`tests/fixtures/business_fixture.json`）专门塞了容易出错的情况：大小写不同、德语变音、中文、越南语、同名的两家店、没有名字的店、文件末尾的空行
- **答案要有"独立的第二个来源"**：Redis 算出来的数字，要和直接从文件算出来的数字一致
- **变异测试**：全部测试通过之后，**故意把代码改坏**，看测试能不能发现

这次的变异测试结果：

| 故意改坏的地方 | 被发现了吗 |
|---|---|
| M1 前缀上界用字符 ÿ 代替字节 0xFF | ✅ 6 个测试失败 |
| M2 名字不转小写 | ✅ 17 个测试失败 |
| M3 详情改成每个 id 发一次 GET | ✅ 效率测试发现了 |
| M4 存储前重新 json.dumps | ⚠️ **一开始没发现！** 原因是集成测试只核对了一条纯 ASCII 的记录。把它改成逐条核对所有记录后就能发现了 |
| M5 没有名字的店也被放进索引 | ✅ 3 个测试失败 |
| M6 不打包，每条命令单独发送 | ✅ 效率测试发现了 |

👉 M4 正好说明了**为什么要做变异测试**：测试全绿，不代表测试本身就是好的。

- **全新环境复现**：在一个全新的容器里，从零跑完整个流程
- **CI**：每次推送到 GitHub，都会自动在 4 种环境（Python 3.10/3.13 × Redis 5/8）里，**从 Sciebo 下载真实数据**，完整跑一遍。CI 还抓到过一个真 bug：Sciebo 的两个下载链接，我在 Linux 版脚本里把哪个是大文件、哪个是小文件写反了

### ✅ 自测
1. 冒烟测试失败了，为什么要停下来，不继续跑后面的？ → 连环境都不对，后面的失败或跳过都没有参考价值
2. 为什么集成测试用 15 号库？ → 测试前后要清空数据，不能清掉 0 号库里的真实数据
3. "效率"是怎么测出来的？ → 先清零 Redis 的命令统计（`CONFIG RESETSTAT`），执行函数，再读 `INFO commandstats`，看执行了哪些命令、各执行了几次
